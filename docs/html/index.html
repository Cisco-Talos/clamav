High-Level Design

ClamAV Engine Atlas

ClamAV is an open-source antivirus toolkit built around a single scanning library, libclamav, with a family of daemons and command-line tools layered on top. This atlas maps the components, the scan pipeline, and where each responsibility lives in the source tree.

System overview

Everything that detects malware lives in libclamav: file-type identification, archive and document extraction, unpacking, pattern matching, and a sandboxed bytecode virtual machine for complex signatures. The tools around it are thin by design:

  • clamscan links libclamav directly for one-shot command-line scanning.
  • clamd loads the engine once and serves scans over a TCP or Unix socket (see the protocol reference); clamdscan, clamdtop, clamonacc (on-access scanning via fanotify), and clamav-milter (sendmail/postfix mail filtering) are its clients.
  • freshclam / libfreshclam download and verify signature databases (CVD/CLD) from mirrors.
  • sigtool, clambc, and clamsubmit support signature authoring, bytecode inspection, and sample submission.

Scan pipeline

Every scan — whether it enters through cl_scanfile(), a descriptor, or an in-memory map — converges on the same recursive pipeline inside libclamav:

cl_scanfile / cl_scandesc / cl_scanmap_*
▼
fmap — map file into memory (fmap.c)
▼ hash lookup — skip if known clean (cache.c) ▼
file-type identification (filetypes.c, magic + type signatures)
▼ dispatch by type (scanners.c) ▼
container parser extracts children (zip, pdf, ole2, pe resources…)↺ recurse on each embedded object
▼ every layer's raw + normalized data ▼
matchers: Aho-Corasick · Boyer-Moore · PCRE · hash sets · YARA rulesbytecode signatures (sandboxed VM)
▼
verdict: CL_CLEAN → cache hash · CL_VIRUS → report name via callbacks

Recursion is bounded by engine limits (max-recursion, max-filesize, max-scansize…) set through cl_engine_set_num(). Scan-phase callbacks (pre_cache, pre_scan, post_scan, file_inspection, virus_found) let embedding applications observe or veto each layer.

Signature databases

Detections come from database files loaded with cl_load(), distributed as signed CVD archives (main.cvd, daily.cvd, bytecode.cvd) and patched incrementally into CLD files by freshclam. Major signature types:

ExtensionTypeMatcher
.hdb / .hsbFile hash (MD5/SHA)Hash table
.ndb / .ldbBody patterns / logical signaturesAho-Corasick + Boyer-Moore, logical expression evaluator
.cbcBytecode signaturesSandboxed bytecode VM (interpreter or JIT)
.pdb / .wdbPhishing URL rules / allow-listsphishcheck / regex
.yar / .yaraYARA rulesEmbedded YARA compiler
.crbAuthenticode certificate trust/blockcrtmgr

Build & layout

The project builds with CMake (CMakeLists.txt, presets in CMakePresets.json) and Cargo for the Rust components, which CMake orchestrates. Windows-specific glue lives in win32/; packaging metadata in vcpkg.json and the Docker notes in README.Docker.md.

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build
